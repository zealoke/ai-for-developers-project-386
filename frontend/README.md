# Frontend

Веб-интерфейс сервиса бронирования встреч (аналог cal.com). Отдельная часть
приложения: работает только через HTTP API по контракту из `../specs`,
собственного бэкенда не содержит и не подразумевает.

Стек: TypeScript, Vite, React 19, Mantine 9, TanStack Query, React Router,
openapi-fetch/openapi-typescript, Vitest, Playwright, Stoplight Prism.

## Роли и разделение интерфейса

Авторизации в контракте нет. Роли разделены только по адресу:

- `/` и `/book/:eventTypeId` — гость: список типов встреч, бронирование.
- `/admin/*` — владелец календаря: типы встреч, график доступности, брони.

## Установка

```sh
npm install
cp .env.example .env
```

## Как это работает с бэкендом

Фронтенд обращается к `VITE_API_BASE_URL` (по умолчанию `/api`). В
разработке запросы на `/api/**` проксирует Vite (см. `vite.config.ts`) на
адрес `DEV_API_TARGET` с добавлением префикса `DEV_API_PREFIX`. Так одним
изменением `.env` можно переключаться между источниками данных:

| Сценарий                      | DEV_API_TARGET          | DEV_API_PREFIX                                                                   |
| ----------------------------- | ----------------------- | -------------------------------------------------------------------------------- |
| Prism mock (без бэкенда)      | `http://localhost:4010` | (пусто)                                                                          |
| Prism proxy → реальный бэкенд | `http://localhost:4011` | (пусто)                                                                          |
| Реальный бэкенд напрямую      | `http://<host>:<port>`  | `/v1`, если бэкенд слушает под этим префиксом (см. `@server` в `specs/main.tsp`) |

В проде `VITE_API_BASE_URL` должен быть абсолютным адресом бэкенда — прокси
Vite в собранном приложении не участвует.

## Типы API

`src/api/schema.d.ts` генерируется командой `npm run gen:api` из
`../specs/tsp-output/openapi3/openapi.yaml` и **не редактируется руками**.
Файл закоммичен в репозиторий (сама папка `specs/tsp-output/` — в
`.gitignore`), поэтому `gen:api` сначала пересобирает TypeSpec-спеку, а
затем прогоняет `openapi-typescript`. `npm run gen:api:check` дополнительно
проверяет `git diff`, чтобы поймать расхождение фронтенда с контрактом в CI.

Поверх сырых типов в `src/api/types.ts` — удобные псевдонимы
(`EventType`, `Booking`, `Slot`, ...), а весь остальной код ссылается только
на них.

## Работа с ошибками API

`src/api/unwrap.ts` превращает ответ `openapi-fetch` в `data` при успехе или
бросает `ApiError`/`NetworkError` (см. `src/api/errors.ts`). Дальше по коду:

| Код ответа                               | Поведение                                                 |
| ---------------------------------------- | --------------------------------------------------------- |
| `VALIDATION_ERROR`                       | `details[].field` → ошибки конкретных полей формы         |
| `SLOT_OUT_OF_RANGE` / `SLOT_NOT_ALIGNED` | уведомление + перезапрос сетки слотов                     |
| `NOT_FOUND` (тип встречи)                | возврат гостя на список типов встреч                      |
| `SLOT_TAKEN` (409)                       | уведомление «время только что заняли» + перезапрос слотов |
| сеть / 5xx                               | общий алерт с кнопкой «Повторить» (см. `QueryBoundary`)   |

## Особенности контракта, важные для фронтенда

- **`AvailabilityInterval`** называется в контракте «интервалом занятости»,
  но `Slots.list` строит сетку доступных слотов именно нарезкой этих
  интервалов — фактически это рабочие окна владельца. В UI (страница
  «График доступности») они подписаны как «интервалы, когда вас можно
  забронировать», расхождение в терминологии зафиксировано здесь и в
  комментарии в коде.
- **Часовой пояс.** Время в ответах API — UTC, но показывается гостю и
  владельцу в часовом поясе владельца (`timeZone` из ответа), а не в поясе
  браузера — иначе группировка слотов по дням (`DaySlots.date`),
  посчитанная сервером, разъедется с тем, что видит пользователь. Пояс
  всегда подписан рядом со временем. Список броней (`BookingListItem`) не
  содержит `timeZone` — он общий для всего календаря, поэтому страница броней
  берёт его из `GET /availability`.
- **`plainTime`** в контракте — формат `HH:mm:ss`, а `TimeInput` Mantine
  работает с `HH:mm`. Конвертация в обе стороны — в `src/lib/datetime.ts`
  (`plainTimeToInputValue`/`inputValueToPlainTime`), покрыта тестами.
- **Слот бронируется как есть.** `start` при `POST /bookings` берётся
  ровно той строкой, что пришла в `Slot.start`, без пересчёта через
  `Date`/dayjs — иначе легко получить `SLOT_NOT_ALIGNED` на округлении.
- **Окно слотов фиксировано сервером** (14 дней от сегодня,
  `rangeStart`/`rangeEnd` в ответе) — на клиенте нет пагинации/навигации
  по неделям за пределы этого окна.
- **У гостя нет способа получить бронь повторно** — контракт не содержит
  `GET /bookings/{id}` для гостя. Поэтому страница успеха бронирования
  получает данные только через `state` роутера сразу после
  `POST /bookings`; при прямом заходе показывает понятное сообщение
  вместо попытки что-то запросить.

## Тестирование

- **Unit (Vitest)** — чистая логика без сети и DOM: `src/lib/*.test.ts`
  (даты/часовые пояса, валидация графика), `src/api/*.test.ts` (разбор
  ошибок API).
- **E2E (Playwright)** — `tests/e2e/`. Сеть **не идёт** ни к Prism, ни к
  реальному бэкенду: `tests/e2e/support/mockApi.ts` перехватывает `**/api/**`
  на уровне браузера и отвечает фикстурами из `tests/e2e/fixtures/`,
  типизированными по контракту. Это делает тесты быстрыми и
  детерминированными (сравните с `prism mock`, который каждый раз генерирует
  случайные данные и не хранит состояние между запросами).
- **`tests/e2e/smoke-real.spec.ts`** — опциональный дымовой тест против уже
  запущенного реального бэкенда (без моков). Пропускается по умолчанию:

  ```sh
  # 1. В .env: DEV_API_TARGET=http://localhost:<порт бэкенда> (+ DEV_API_PREFIX при необходимости)
  # 2. Запуск:
  E2E_REAL_BACKEND=1 npm run test:e2e -- smoke-real
  ```

- **Сверка контракта:** `npm run proxy -- <адрес бэкенда>` поднимает Prism в
  режиме validation proxy — он логирует в консоль любые расхождения запросов
  и ответов реального бэкенда с `openapi.yaml`. Полезно гонять вручную (или
  через `smoke-real.spec.ts` с `DEV_API_TARGET=http://localhost:4011`) после
  изменений в `specs/` или в бэкенде.

## Структура

```
src/
  api/            клиент openapi-fetch, типы, обработка ошибок, хуки TanStack Query
  lib/            даты/часовые пояса, дни недели, клиентская валидация
  components/     общие компоненты (layout, QueryBoundary, TimeZoneNote)
  features/
    guest/        список типов встреч, бронирование, экран успеха
    admin/        типы встреч, график доступности, список броней
  App.tsx         роутинг и провайдеры (Mantine, TanStack Query, Modals, Notifications)
tests/
  e2e/            Playwright: фикстуры, мок сети, сценарии
```

## Известные ограничения / что можно улучшить

- Бандл продакшн-сборки ~208 KB gzip — в основном Mantine. Можно уменьшить
  code-splitting'ом админского раздела через `React.lazy`, если размер
  станет критичным.
- Полей `VALIDATION_ERROR` для `PUT /availability` нет постатейной привязки
  к конкретным интервалам — сообщение сервера показывается общим
  уведомлением (в отличие от форм типов встреч и бронирования, где есть
  постатейная разбивка по `details[].field`).
